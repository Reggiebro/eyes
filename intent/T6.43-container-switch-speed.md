## Why

A `wrangler deploy` took 3 to 25 minutes before the new image served, then a 5 to 15 s gap of failed requests. A rollout replaces an instance by sending SIGTERM and waiting up to 15 minutes before SIGKILL. The server had no SIGTERM handler, and node running as PID 1 ignores SIGTERM unless it has one (checked locally: `docker stop -t 20` on `node:26-slim` waited the full 20 s). The Durable Object only retried while booting, so requests during the switch failed. `basic` is 0.25 vCPU, which makes the boot slow.

## What changed

- `apps/mcp/src/main.ts`: `onSigterm` stops the expiry sweep and new connections, exits 0 once open requests finish or after `DRAIN_MS` (10 s), so most `await_answer` polls finish.
- `apps/edge/api/worker.js`: `EyesServer.fetch` retries only on the two runtime errors that mean nothing reached the server ("the container is not listening", "there is no container instance that can be provided"), and calls `ensure()` between retries so the new instance starts as soon as the old one exits. Any other error answers 502 at once, never a replay. Bodies up to 1 MB (declared `content-length`) are buffered so they can be replayed. Larger or unknown-length bodies are streamed once the server is up; a refusal answers 503 and the next request waits for the restart.
- `wrangler.jsonc`: `instance_type` `standard-1` (0.5 vCPU, 4 GiB, 8 GB disk). Run 24/7 this adds about $20/month: 3 GiB more memory at $0.0000025/GiB-s ($19.44) plus 4 GB more disk at $0.00000007/GB-s ($0.73). CPU is billed on active use, so it does not change.
- `docs/DEPLOY.md` step 2: deploy with `--var EYES_COMMIT:<sha>` so `/status` names the serving build, and the switch behaviour.

## Verification

- `main.test.ts`: a spawned server exits 0 within 10 s of SIGTERM; `onSigterm` exits on close and at `DRAIN_MS` with a request still open.
- `worker.test.ts`: replay after refusal and no-instance; 503 after 60 s; 502 with no replay on "Network connection lost."; a rollout swap holds the request and starts the new instance; large and chunked bodies stream; streamed body 503/502 without replay.
- Live, deploy of 90963ab (2026-10-18 08:36Z, old server still without the SIGTERM handler; `/healthz` and `/status` probed every 2 s): `wrangler deploy` 75 s; the new build first answered at +341 s (5.7 min); 2 probes got 502 (+337 s, +339 s), so about 4 s of errors; no other non-200. `containers info`: 0.5 vCPU, 4 GiB. `POST /w/device` without auth still answers 401.

## Known gaps

- The first deploy of this change still waits up to 15 minutes: the old server, built before this change, ignores SIGTERM.
- `await_answer` polls longer than 10 s at the switch are cut; the agent calls again.
- A true zero-gap switch needs two servers at once (the `durable_object` scheduling policy, blue/green by image); not done.
