## Why

Let clients request a new quote after a wrong answer and let operators review repeatedly disputed workers without automatically confiscating pay or permanently banning them.

## Rules

- A new genuine dispute evaluates distinct tasks since the last operator review. Existing `tasks.test` rows never count; repeated reports and re-disputing the same task never add another count. The first ticket id is compared with a review checkpoint, not a rolling time window or timestamps. Migration does not backfill holds: historical unreviewed genuine tasks count only when a new genuine task is disputed.
- Three tasks set `workers.dispute_hold_at`. Worker-first locks serialize disputes, review, claims and offer persistence; fraud decisions take the same worker-first order. Nearby, pings, reoffers, late offer expansion, stale post-task candidates and shared phone/email sends exclude held or permanently banned workers. An already-issued offer cannot be newly claimed after the hold. Already-claimed capture and payout remain valid; no hold/review operation touches balances, ledger, current task ownership, location, opt-in or the permanent `banned` flag.
- Authenticated internal GET/POST `/ops/workers/:id/dispute-review` reuse operator sessions and the exact-Origin CSRF guard for POST. Review requires a 5–1000 character note, clears only the temporary hold, records actor/time/`lift_hold`/note in existing events, and advances the ticket checkpoint. A permanent fraud ban survives review. Support disputes still resolve individually with unchanged refund/reversal/payout semantics.
- `get_task` and `dispute_answer` return `retry_context: {question, location: {lat,lng,label}, task_type, bounty_usd}` from the stored task. Ask again calls existing `quote_task` for free; creating a replacement requires explicit confirmation, a fresh idempotency key and all normal safety/spending rules. No dispute automatically creates or pays for another task.
